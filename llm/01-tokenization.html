分詞Tokenization

模型看不懂文字，只看得懂整數。在任何「理解」發生之前，文字必須先被切成一個個 token、再換成編號。這一章看三件事：該切多細、BPE 怎麼自己長出詞彙表，以及 token 數為什麼直接決定成本。

      § 1.1模型只認得數字

      神經網路的輸入是一串向量，而向量要從一張查找表裡取出來——所以文字得先變成「第幾號」。問題是：要以什麼為單位編號？

      最直覺的兩種做法各有致命傷。以字元切，詞彙表很小、永遠不會遇到不認識的字，但序列會變得很長，模型得花大量運算去重新拼出「字」的概念。以單字切，序列很短，但詞彙表會膨脹到上百萬，而且只要遇到新詞、錯字或專有名詞，就只能標成 [UNK]（未知）。

      現代 LLM 幾乎都選擇中間路線：子詞（subword）。常見的詞整個收進詞彙表，罕見的詞拆成幾個常見片段，最壞情況退回單一位元組——既不會遇到未知字，序列也不會太長。

      § 1.2BPE：讓詞彙表自己長出來

      子詞詞彙表不是人工編的，而是從語料「統計」出來的。最常見的演算法是 BPE（Byte Pair Encoding，位元組對編碼），GPT 系列與 Llama 都使用它的變體。規則只有一條，反覆執行：

      1. 把所有詞拆成最小單位（字元或位元組），作為初始詞彙表。
      2. 數一數語料中哪一對相鄰符號最常一起出現。
      3. 把這一對合併成一個新符號，加進詞彙表。
      4. 回到第 2 步，直到詞彙表達到預設大小。

      下面的圖版真的在瀏覽器裡執行這個演算法。注意兩件事：每次合併後語料的 token 總數都在下降，而高頻的整個詞（像 newer）最終會變成單一 token。

      註

      實務上的 BPE 從 256 個位元組出發（byte-level BPE），所以任何語言、任何 emoji 都能被表示，永遠不會有未知字。GPT-2 的詞彙表約 5 萬個 token，近年的模型則常見 10 萬到 20 萬。

      § 1.3Token、ID 與詞彙表

      訓練好的分詞器就是一張詞彙表加上一份合併規則。每個 token 對應一個整數 ID，模型真正收到的是這串 ID；在第 02 章，每個 ID 會再被換成一個嵌入向量。

      幾個常讓人意外的細節：空白通常黏在下一個詞的前面（「␣model」和「model」是兩個不同的 token）；大小寫不同也是不同 token；詞彙表沒收錄的字會退回位元組，一個中文字在 UTF-8 裡佔 3 個位元組，最壞就變成 3 個 token。

      § 1.4為什麼 token 數很重要

      對 LLM 來說，token 是一切的計量單位：

      • 成本——API 依輸入與輸出的 token 數計費。
      • 上下文長度——「128K 上下文」指的是 12.8 萬個 token，不是字數。
      • 速度——模型一次生成一個 token（第 05 章），輸出越多 token 越慢。
      • 運算量——注意力的計算量隨序列長度平方成長（第 03 章）。
      費用 ≈ 輸入 tokens × 輸入單價 + 輸出 tokens × 輸出單價
      // 英文經驗值：1 個 token ≈ 4 個字元 ≈ 0.75 個英文單字

      這也解釋了中英文的效率差異。分詞器的語料若以英文為主，英文常用詞多半一個 token 就搞定，中文卻可能一個字一個 token，甚至被拆成位元組。同樣的意思，中文可能要用更多 token——也就是更貴、更快把上下文塞滿。新一代分詞器擴大了多語詞彙，差距已明顯縮小，但仍因模型而異。

      註

      分詞也解釋了 LLM 的一些「怪」行為：問它 strawberry 有幾個 r 常會答錯，因為模型看到的是「str」「aw」「berry」這類片段的 ID，而不是一個個字母。

      § 1.5本章重點

      1. 模型只處理整數 ID；分詞器負責把文字切成 token 並編號。
      2. 字元級序列太長、單字級詞彙表太大且有未知詞，子詞是兩者的折衷。
      3. BPE 反覆合併最常見的相鄰配對，從語料統計出詞彙表。
      4. byte-level BPE 以位元組為底，任何文字都能表示，代價是罕見字會變成多個 token。
      5. 成本、上下文長度與生成速度都以 token 計，同樣內容在不同語言下的 token 數可能差很多。
